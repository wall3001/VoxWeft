# TTS 首响与音质体检 — 2026-09-12

针对「首响慢、播放噪声」两个报告的排查记录。**结论分三类：已修复、
已证伪、未证实**。三类都要记下来，否则下次还会重查一遍。

---

## 一、已修复：冷启动首响（确凿）

### 现象

同一句话、同一服务，TTS 首块延迟：

| 状态 | 首块延迟 |
|---|---|
| 进程启动后第一次请求 | **2149 ms** |
| 之后的热态请求 | **62 ms** |

差 35 倍。展厅演示时这就是「第一句话卡住两秒」。

### 根因

`m3_bridge.py` 的两个模型都是**首次请求才加载**（`_get_tts()` / `_get_asr()`
里的惰性单例），启动时不做任何预热。第一个真实请求要付：加载权重 +
首次推理的图编译。

### 修法

`m3_bridge.py` 的 `__main__` 加开机预热：后台线程加载 TTS + ASR，
各跑一次真实推理路径（不只是加载权重——编译/缓存在这一步才建好）。
放后台线程是为了不阻塞 uvicorn 起来（否则 launchd 的健康检查会以为服务没起）。

预热失败只记 warning 并回退懒加载，不影响服务可用性。

### 验证

```
warmup: TTS loaded in 1.5s
warmup: TTS primed in 0.2s
warmup: ASR primed in 0.9s
warmup done (total 2.6s)
```

预热后首个可播块稳定在 **124-168 ms**（此前冷启动 2149 ms）。

> 注意口径：`tts_check.py` 报的「首块延迟」是 **HTTP 首字节**，不含进程内
> 延迟；「首个可播块」才是客户端真正开始能播的时刻。两者差约 50ms。
> 只有后者是北极星口径。

## 二、已证伪：不是解码器、不是量化、不是参数

排查「噪声」时逐一排除了这些假设，证据都留着，免得重查。

### 流式 VAE 解码器 —— 无罪

同一份 latents，分别走流式逐帧 / 流式一次喂全 / 非流式整段，三种路径
输出**逐位相同（差异 0.0%）**。`StreamingVAEDecoder` 的状态管理是正确的。

### 4bit 量化 —— 无罪

怀疑 `quantize_lm=4` 的精度损失累积。实测对照（各 5 次）：

| | 时长波动 | 周期性中位 | SNR 中位 |
|---|---|---|---|
| `quantize_lm=4` | 1.44 s | 0.315 | 29.0 dB |
| `quantize_lm=None` (bf16) | 1.76 s | 0.219 | 26.6 dB |

bf16 并不更好（周期性反而更低）。量化不是元凶，省下的内存可以留着。

### temperature —— 语义被误解

VoxCPM2 的 `temperature` **不是采样温度**，而是流匹配起点的噪声方差
（`model.py:304`：`z = mx.random.normal(...) * temperature`）。

- `temperature=1.0` 是官方默认，必须保留。
- **调低会坏**：`t=0.01` 时起点方差近零，模型失去生成所需的随机性 →
  不收敛、不吐 stop、输出噪声（实测跑满 80s 上限不退，80% 帧是静音）。

这条值得单独记住：`temperature` 看起来像能治「抖动」的旋钮，实际上
调它只会让事情更糟。

### 参数组合 —— 调参救不了

`inference_timesteps ∈ {6,10,15}` × `cfg_value ∈ {1.0,1.5,2.0,3.0}` 全矩阵
跑下来，没有任何组合能消除方差。单次实验的方差本身就大到掩盖调参效果。

## 三、未证实：所谓「噪声」

**我无法证实链路存在系统性噪声。** 反向证据：

| 检查项 | 结果 |
|---|---|
| ASR 回环（合成→重识别） | 每次都准确转写，与原文一致 |
| 削波 | 0.000% |
| 直流偏置 | ~1e-4，可忽略 |
| 首尾跳变 | 无（起止都是零） |
| 高频能量（>8kHz） | 0.4%，正常语音滚降 |
| chunk 边界跳变 | 不超过全曲 p99.9 差分 |

能观察到的**真实波动**是**时长与响度**：同一文本、同一参数，6 次生成的
时长在 3.84–6.40s 之间、SNR 在 26.9–66.7 dB 之间。

这更像**随机生成模型的正常表现**（无种子、每次独立采样），而不是故障：
如果波形有噪声，ASR 回环不会次次都对。

**待你在现场确认**：如果人耳确实听到噪声，最有嫌疑的是**播放链路**而非
服务端。已按这个方向修了两处客户端问题（见下）。

### 已修的客户端播放问题（真问题，但未在实机验证）

1. **抖动缓冲**：服务端按 200ms 一块发，但 WS 消息边界不一定与它对齐。
   原先每收到一小段就 `scheduleBuffer` 一次，节点会在每个 buffer 边界各自
   衔接，听感是周期性「咔」。现在攒够 200ms 再交给节点。
2. **`stopPlayback` 语义**：`player.stop()` 会丢弃已排队的 buffer（打断
   想要的效果），但必须紧接着 `play()`，否则节点停在 stopped 状态，
   后续到达的块只入队不播放。

> 这两处**只在 macOS 上编译通过，没有实机听过**。SSH 拿不到 GUI 会话的
> 屏幕/音频，验证需要人在机器前操作。

## 四、复现用的脚本

> 这些探针脚本是展台构建的一部分，**未随本仓库发布**；等价的检查见 `scripts/probe_onset.py`、`scripts/probe_stream.py` 与 `bench/bench_tts.py` + `bench/judge_tts.py`。下面保留原始命令仅作记录。

| 脚本 | 用途 |
|---|---|
| `tts_check.py` | 首响 + 波形体检（DC/削波/首尾/块边界） |
| `tts_quality.py` | ASR 回环 + 频谱 + 底噪/周期性 |
| `tts_sweep.py` | 参数扫描（流式/非流式、cfg、temperature） |
| `tts_stability.py` | 同参数重复 N 次，测离散度 |
| `tts_quant.py` | 量化 vs bf16 对照 |
| `tts_tune.py` | timesteps × cfg 矩阵 |

都直接在 M3 上跑：

```bash
python tts_check.py --lang zh --repeat 3
```
